# Audit log — 2026-10-20 (code-logic verification pass)

Continuation of `audit_2026-10-19.md`. Question put to this pass: *the test
suites are green (139/139) — is the CERPS code logic actually correct?*
Green tests only assert the properties they were written for, so this pass
audited the parts the suites do **not** cover, with an emphasis on options
that are *silently* ignored or that only misbehave outside the default
configuration.

Every finding below was **measured before and after the fix** (not inferred
from reading the code).

---

## 1. `simulator.py:_record` — silent cell loss for G >= 4 genes (D1)

**Defect.** `classify_legacy` (`rates.py`) emits labels `0..G`: `0` = all
genes high, `j+1` = gene `j` high alone. `_record` hard-coded the columns
`{0, 1, 3}` plus an explicit count of label `2`, so for `G >= 4` the states
above label `3` had no column and were dropped from **every** `ho_*`
aggregate and from `transitions()`-derived summaries.

**Measured.** `sc + ta1 + ta2 + other` vs `total`:

| G | missing cells |
|---|---|
| 2 | 0 |
| 3 | 0 |
| 4 | **20.3 %** |
| 5 | **30.8 %** |

`G = 3` is the largest gene number used in the repository's examples, which
is why no test caught it.

**Fix** (`simulator.py:99-106`). `other` is now the **residual**
`n - sc - ta1 - ta2`, so the decomposition is exact for any `G`. For `G = 2`
the residual is `0` (labels are `0/1/3`) and for `G = 3` it reduces to the
old explicit count of label `2`, so both are unchanged.

## 2. `simulator.py` — P6 leaky integrator diverges below one step (D2)

**Defect.** The P6 memory update used the unclamped EWMA gain `dt / tau`.
For `tau < dt` this exceeds 1 and the explicit Euler step overshoots, which
compounds because the driver is itself a function of the state.

**Measured** (`tau = 0.1`, `dt = 0.25`, i.e. `dt/tau = 2.5`):
`mem` reached `|mem| ~ 1e174`. Any run with `mem_couple != 0` and a
sub-step memory timescale therefore produced garbage kinetics.

**Fix** (`simulator.py:184`). `gain = min(1.0, dt / max(tau, 1e-12))`.
Measured after the fix, for `tau` in `{10, 1, 0.25, 0.1, 0.01}`
(`dt/tau` up to 25): `mem` stays inside `[0.0001, 0.9524]` and finite in
every case — consistent with the driver being a stemness fraction in
`[0, 1]`.

**Note.** Clamping is the conservative resolution: a timescale shorter than
one step is unresolvable by an explicit integrator, so the gain saturates
instead of exploding. `batch.validate()` now says so explicitly (D3).

## 3. `config.py:MemoryConfig.driver` — a dead option (D3)

**Defect.** `MemoryConfig.driver` ("stemness", line 123) is never read
anywhere: the integrator always uses the stemness signal. A user selecting a
non-default driver would silently get the default behaviour — the exact
class of option that invalidates a mechanism comparison without any error.

**Fix** (`batch.py:170-176`). `validate()` now warns when
`memory.enabled and driver != "stemness"`, and separately when
`memory.enabled and tau < dt`. Both messages name the consequence rather
than just the value. The option itself is left in place (removing it would
be a breaking API change); it is now *documented as ignored* instead of
*silently honoured*.

---

## 4. `simulator.py:run` — P8 delay buffer not reset between calls (D4)

**Defect.** `step` is a **local** loop index starting at `0`, while
`_q_hist` is instance state initialised once in `__init__`. Calling `run()`
twice on the same `Simulator` (a natural way to continue a run with a larger
`t_max`) therefore indexes history entries from the *previous* call and
applies the wrong delayed feedback — silently, with no exception.

**Measured.** Instrumented `effective_niche_signal` to count calls whose
`step` index exceeded the history length (i.e. cross-generation reads). With
a segmented `run(200) + run(200)` against `delay_steps = 20`:

| | before | after |
|---|---|---|
| cross-segment stale reads | > 0 | **0** |

**Fix** (`simulator.py:120`). `self._q_hist = []` at the top of `run()`.
Documented semantics: each `run()` call restarts the delay history, so the
first `delay_steps` steps of a continuation fall back to the instantaneous
signal. This is a deliberate, stated behaviour rather than an accident.

**Scope.** No current caller is affected: every call site in `batch.py`,
`tests/` and `reproduction/` constructs a fresh `Simulator` and calls
`run()` once. The fix closes a latent trap for interactive/continuation use.

## 5. Checked and found correct (no change)

Recorded so the next pass does not re-derive them:

- **P8 delay indexing.** `q_now` is appended *before* the read, so
  `hist[step]` is the current step; `hist[step - d]` is the delayed value;
  `step < d` falls back to `current`. Confirmed by direct evaluation:
  `d=0 -> 0.3` (current), `d=2 -> 0.5` (`= hist[1]`, genuinely delayed),
  `d=5 > step -> 0.3` (fallback).
- **P6 gating.** Label updates happen only on resting cells; the memory
  integrator is entered only when `cfg.memory.enabled`.
- **m2 = 0.8/1.0 discrepancy.** Already documented in `protocol_notes.md`
  as a paper-internal inconsistency, not a code defect.
- **`transitions()` label space** uses the generic `[0] + range(1, G+1)`,
  consistent with `classify_legacy` — the mismatch was only in `_record`.
